# 정리 후보 탐지와 안전한 정리

## 탐지 규칙

| 유형 | 폴더 | 파일 |
|---|---|---|
| Node.js | `node_modules` | – |
| 빌드 결과물 | `dist`, `build`, `out`, `cmake-build-*`, `target`\*, `bin`\*, `obj`\* | – |
| 개발 캐시 | `.cache`, `.next`, `.nuxt`, `.vite`, `.parcel-cache`, `.turbo`, `.svelte-kit`, `.angular`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.tox`, `.nox`, `.hypothesis`, `.gradle`\*, `.vs`\* | – |
| 임시 파일 | `.tmp`, `.temp` | `*.tmp` |
| 로그 | – | `*.log`\*\* |

\* 같은 폴더에 해당 프로젝트 표시 파일이 있을 때만 후보입니다(`target`: `Cargo.toml`·`pom.xml`, `bin`·`obj`·`.vs`: `*.csproj`·`*.fsproj`·`*.vbproj`·`*.sln`,
`.gradle`: Gradle·Maven 파일). 그래서 사용자 폴더의 `bin`이나 홈의 `.gradle`(설정·인증 정보 포함)은 후보가 되지 않습니다.

\*\* LevelDB 데이터베이스의 쓰기 로그는 이름이 `.log`여도 후보가 아닙니다. Chrome·Edge·VS Code 등 Chromium/Electron 앱이 로컬 저장소·
IndexedDB·확장 상태·세션을 LevelDB로 저장하며, 아직 본 파일에 합쳐지지 않은 데이터가 이 파일에 있어 지우면 데이터가 사라질 수 있습니다.

- 이름이 숫자 6자리 이상뿐인 `.log`(`000003.log`)는 로그로 보지 않습니다. 날짜만으로 이름을 지은 로그(`20261106.log`)도 함께 빠집니다.
- 같은 폴더에 LevelDB 표시 파일(`CURRENT`·`LOCK`·`MANIFEST-*`)이 있으면 그 폴더의 `*.log`는 모두 후보에서 뺍니다.

개발 환경은 폴더 이름(예: `__pycache__` → Python)이나 같은 폴더의 표시 파일(`package.json`, `pyproject.toml`·`requirements.txt`,
`Cargo.toml`, `pom.xml`·`build.gradle`, `*.csproj`·`*.sln`, `CMakeLists.txt`·`Makefile`, `go.mod`)로 정하고, 정할 수 없으면 '일반'입니다.
`node_modules`와 빌드 결과물은 표시 파일이 있으면 **확인됨**, 없으면 **추정**으로 표시합니다.
먼저 맞은 폴더가 그 아래 전체를 차지하므로(`node_modules\pkg\dist`는 따로 나오지 않음) 항목 용량의 합에 중복이 없습니다.

## 파일 삭제 안전성

- 탐지는 이름·크기·속성만 읽고 파일을 열거나 수정하지 않습니다. 정리 과정에는 영구 삭제 코드 경로가 없습니다
  (영구 삭제는 [격리 폴더](#격리-폴더) 탭에서 사용자가 고르고 두 번 확인한 항목에만 합니다).
- 휴지통 이동은 `IFileOperation`(`FOF_ALLOWUNDO | FOFX_RECYCLEONDELETE`)으로 항목마다 실행합니다. 셸이 영구 삭제로 바꾸려 하면
  (휴지통 용량 초과 등) 진행 싱크에서 거부하고, 항목이 그대로면 다시 확인한 뒤 격리 폴더로 옮깁니다.
- 다음 중 하나라도 해당하면 그 항목은 건드리지 않습니다.

| 시점 | 거부 조건 |
|---|---|
| 경로 판정 | UNC·상대 경로, 260자 이상, 탐지 경로 밖이거나 탐지 경로 자체 |
| | Windows·`Program Files`·`ProgramData`, 볼륨 루트의 `$Recycle.Bin`·`System Volume Information` 등과 같거나 그 아래 |
| | 개발 도구·프로그램 설치 경로와 같거나 그 아래([보호 경로](#보호-경로)) |
| | 볼륨 루트, `Users`, 사용자·공용 프로필, 바탕 화면·문서·다운로드 등 알려진 폴더, `AppData`, 실행 중인 프로그램 폴더, 그리고 이들의 상위 |
| | 하위를 다 읽지 못한 항목(접근 거부·취소로 일부 누락) |
| | 격리 폴더(`.bytesieve-trash`)이거나 그 안 |
| 옮기기 직전 | 고정·이동식 드라이브가 아님(네트워크·CD 등), 이미 없음 |
| | 탐지 때와 종류가 다름, 링크로 바뀜, `GetFinalPathNameByHandleW`로 구한 실제 위치가 표시 경로와 다름(중간 폴더가 정션으로 바뀐 경우 등) |

### 보호 경로

다음 경로는 탐지할 때 **들어가지 않고**(그 안의 실행 파일·`node_modules`·`__pycache__`·`out`·`*.log` 등은 후보가 되지 않음),
정리 판정에서도 그 경로와 그 아래를 거부하며 그 상위(예: `AppData\Local`)는 중요 경로로 거부합니다.
[프로젝트 정리] 탭의 탐지·휴지통 이동과 [시스템 정리] 탭이 모두 같은 목록(`cleanup_protect_add_system`)을 씁니다.

| 경로 | 예 |
|---|---|
| `%WINDIR%`, `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%ProgramW6432%`, `%ProgramData%` | Visual Studio·VS Code 시스템 설치의 기본 위치 |
| `%LOCALAPPDATA%\Programs` | VS Code 사용자 설치(`Microsoft VS Code`), Python 등 사용자별 설치 프로그램 |
| `%USERPROFILE%\.vscode\extensions`, `%USERPROFILE%\.vscode-insiders\extensions` | 설치한 VS Code 확장(안에 `package.json`·`node_modules`가 있어 예전에는 후보가 될 수 있었음) |
| 프로그램 제거 정보(레지스트리 `Uninstall`, HKLM 64·32비트와 HKCU)의 `InstallLocation` | 표시 이름이 `Microsoft Visual Studio…`·`Visual Studio …`인 항목. 다른 드라이브(`D:\VS` 등)에 설치한 Visual Studio·VS Code |

레지스트리 값은 앞뒤 공백·따옴표를 벗기고 `X:\폴더` 꼴의 로컬 절대 경로만 받습니다. 볼륨 루트(`D:\`)는 드라이브 전체가 보호되어
탐지가 멈추지 않도록 받지 않습니다. 사용자가 보호 경로 안을 직접 탐지 경로로 고르면 항목은 보여 주되 모두 보호 표시를 붙여 옮기지 않습니다.
압축 파일로 푼 VS Code(포터블)처럼 위 어디에도 등록되지 않은 위치는 알 수 없습니다.

### 앱 데이터 폴더

[프로젝트 정리] 탭의 탐지는 위 목록에 더해 **앱 데이터 폴더 안의 앱별 폴더**에도 들어가지 않습니다(`cleanup_protect_add_app_data`).
브라우저·편집기·IDE가 데이터베이스(LevelDB 등)·설정·내려받은 도구를 두는 곳이라, 이름이 `*.log`·`node_modules`여도 데이터나 도구의
일부일 수 있기 때문입니다(예: Chrome·Edge 저장소, VS Code 세션 저장소, JetBrains IDE가 내려받은 도구의 `node_modules`).

- 대상: `%LOCALAPPDATA%`·`%APPDATA%`·`%USERPROFILE%\AppData\LocalLow` 바로 아래의 폴더(탐지를 시작할 때 있는 것). 그 아래 `Temp`는
  임시 폴더라 계속 탐지합니다.
- 앱 폴더 안을 직접 탐지 경로로 고르면 보호 경로와 같이 항목은 보여 주되 보호 표시를 붙여 옮기지 않습니다.
- [시스템 정리] 탭의 공용 개발 캐시는 이 목록을 쓰지 않습니다. npm·pip 캐시가 `%LOCALAPPDATA%` 아래에 있어서이며, 캐시 구조를 확인한 폴더만 다룹니다.

## 공용 개발 캐시

[시스템 정리] 탭의 개발 도구 캐시(`dev_cache`)는 npm·pip·Gradle·Cargo·NuGet의 공용 캐시를 찾습니다(예전 [공용 캐시] 탭).
위치를 정하는 순서는 [gui.md](gui.md#시스템-정리)에 있습니다. 정리는 위 안전 장치를 그대로 거치며, 캐시마다
**그 캐시 폴더의 부모(도구 폴더)를 탐지 경로**로 삼아 판정합니다(Cleaner 항목의 `root`). 공용 캐시에는 다음을 더 지킵니다.

| 조건 | 처리 |
|---|---|
| 도구 폴더 자체(`.gradle`·`.cargo`·`.nuget`) | 항목으로 만들지 않음. 그 안의 캐시 하위 폴더만 다루므로 설정(`gradle.properties`)·인증 정보·설치한 도구(`.cargo\bin`)는 남음 |
| 환경 변수·설정 파일이 가리킨 폴더 | 그 도구의 캐시 구조(예: npm은 `_cacache`, pip은 `http`·`wheels`, NuGet 패키지는 `<id>\<버전>\.nupkg.metadata`)가 보일 때만 정리 후보. 아니면 `캐시 구조가 아니라 정리하지 않음` |
| 바꾸지 못한 변수(`%NOPE%`)·상대 경로만 있는 환경 변수 | 쓰지 않고 다음 위치로 |
| 링크(정션·심볼릭 링크)인 캐시 폴더 | 정리하지 않음(목록에 이유와 함께 남김) |
| 용량을 다 세지 못함(읽기 오류·취소) | 정리하지 않음 |
| 캐시 위치가 사용자 프로필·문서 등 중요 경로이거나 그 상위 | 거부(위 경로 판정) |
| 캐시 위치가 프로그램 설치 경로 안(Visual Studio의 `Shared\NuGetPackages`, `%LOCALAPPDATA%\Programs` 아래 Node.js의 npm 캐시 등) | 캐시 구조가 맞아도 거부(`보호: 시스템·프로그램 보호 경로`) |

## 격리 폴더

휴지통이 없는 드라이브(USB·외장 드라이브 등 이동식 드라이브)이거나 휴지통에 넣을 수 없는 항목은 영구 삭제하지 않고
**같은 드라이브의 격리 폴더**로 옮깁니다.

| 상황 | 처리 |
|---|---|
| 고정 디스크 | 휴지통으로 이동(기존과 같음) |
| 고정 디스크인데 셸이 영구 삭제하려 함(휴지통 용량 초과·휴지통 없는 볼륨) | 거부한 뒤 항목을 다시 확인하고 격리 폴더로 |
| 고정 디스크인데 셸이 항목을 건드리지 못하고 실패 | 다시 확인한 뒤 격리 폴더로 |
| 휴지통이 일부를 옮긴 뒤 실패 | 휴지통과 격리 폴더로 나뉘지 않게 실패로 남김 |
| 이동식 드라이브 | 처음부터 격리 폴더로 |

```
X:\.bytesieve-trash\                    격리 폴더(숨김, 드라이브마다 하나)
  20261031-153012-1\                    항목 폴더(격리한 시각 + 번호, 같은 이름도 겹치지 않음)
    entry.txt                           기록: 원래 경로, 볼륨 기준 상대 경로, 시각, 종류, 용량, 상태
    f\<원래 이름>                        격리된 파일·폴더
```

- **옮기기**: 같은 볼륨 안에서 이름만 바꿉니다(`MoveFileExW`, 복사·덮어쓰기 없음). 기록을 먼저 쓰고(`state=moving`) 옮긴 뒤 고칩니다
  (`state=moved`). 기록 파일은 임시 파일에 쓴 뒤 바꿔치기합니다. 옮기지 못하면 기록과 빈 폴더만 지우고 원래 항목은 그대로 둡니다.
- **제외**: 폴더 스캔(GUI, CLI 기본·`--jsonl`·`--track`)과 정리 후보 탐지는 격리 폴더에 들어가지 않고, 정리 보호 판정은 격리 폴더 안의
  항목을 거부합니다.
- **복원**: 원래 위치로 이름을 바꿔 돌려놓습니다. 같은 이름이 있으면 덮어쓰지 않고 건너뛰며, 처리 방법을 안내하고
  `이름 (복원됨).확장자`처럼 다른 이름으로 복원할지 묻습니다. 없어진 상위 폴더는 만듭니다. 드라이브 문자가 바뀌었어도
  기록의 상대 경로로 지금 드라이브 기준 위치에 복원합니다.
- **영구 삭제**: 대상 목록·용량과 복구할 수 없다는 안내를 보여 주고 두 번 확인받습니다. 항목 폴더가 격리 폴더 바로 아래이고
  격리 폴더가 링크가 아닌 실제 폴더인지(`GetFinalPathNameByHandleW`) 다시 확인한 뒤 지웁니다. 정션·심볼릭 링크는 따라가지 않고 링크만 지웁니다.
  파일·폴더를 하나 지울 때마다 진행을 알리고(`quarantine_purge_with`), 사용자가 멈추면 남은 파일과 기록은 그대로 둔 채
  `취소함`(`cancelled`)으로 끝납니다. 하위 항목의 속성은 폴더를 읽을 때 받은 값을 써서 파일마다 다시 조회하지 않습니다.
- **예외 처리**: 권한 부족·쓰기 금지, 다른 프로그램이 사용 중, 디스크 공간 부족(기록을 쓰지 못함), 같은 이름, 다른 볼륨, 격리 폴더가
  링크·파일로 바뀜을 구분해 항목별 결과로 보여 줍니다. 일부가 실패해도 나머지는 계속 처리합니다.

### 기록과 실제 상태가 어긋날 때

파일을 지우지 않고 상태로만 보여 주며 처리는 사용자가 정합니다.

| 상태 | 뜻 | 복원 | 영구 삭제 |
|---|---|---|---|
| 격리됨 | 기록과 파일이 모두 있음(기록이 `moving`이어도 파일이 옮겨져 있으면 정상) | 가능 | 파일과 기록 |
| 기록만 있음 | 격리된 파일이 없음 | 불가 | 기록과 빈 폴더만(다른 파일이 있으면 남김) |
| 기록 없음 | 기록이 없거나 손상됨, 상대 경로가 볼륨 밖을 가리킴, 사용자가 넣은 파일 | 불가(원래 위치 모름) | 그 항목 전체 |

## 시스템 정리

[시스템 정리] 탭(`cleaner`)은 프로젝트 밖의 시스템 정크와 공용 개발 캐시를 정리합니다. 대상과 화면은 [gui.md](gui.md#시스템-정리)를 참고하세요.

- 휴지통 비우기를 뺀 모든 항목은 항목마다 위의 [파일 삭제 안전성](#파일-삭제-안전성) 안전 장치(경로 판정 → 옮기기 직전 확인 → 옮기는 중 확인)를
  그대로 거쳐 휴지통으로, 휴지통이 없는 드라이브는 [격리 폴더](#격리-폴더)로 옮깁니다. 분석 때도 경로 판정을 통과한 항목만 정리 대상입니다.
- 탐지 경로: 임시 파일·오류 보고서는 그 폴더(`%TEMP%` 등), 브라우저 캐시는 프로필 폴더, 개발 도구 캐시는 도구 폴더입니다.
  탐지 경로 자체는 옮기지 않습니다(임시 폴더·프로필 설정은 남음).
- 임시 파일·오류 보고서는 최근 24시간 안에 바뀌었거나 만들어진 항목(폴더는 안의 파일 포함)을 빼고, 실행 직전에 다시 확인합니다.
  확인하지 못한 항목도 옮기지 않습니다.
- 브라우저 캐시는 그 브라우저(`chrome.exe`·`msedge.exe`·`firefox.exe`)가 실행 중이면 분석·실행 모두에서 정리하지 않습니다. 실행 여부를 확인하지 못하면 실행 중으로 봅니다.
- `C:\Windows\Temp`·Windows 업데이트 캐시는 보호 경로(Windows 폴더)라 대상이 아닙니다.
- 개발 도구 캐시는 [모두 선택]에 들어가지 않습니다(`cleaner_target_manual_only`). 사용자가 직접 체크해야 하며,
  정리 뒤 오프라인 빌드가 안 되는 캐시(`dev_cache` 의 caution: Gradle 래퍼 배포판·NuGet 전역 패키지)는 `cleaner_target_caution` 으로
  목록·선택 요약·확인 창에 주의로 표시합니다.
- **휴지통 비우기는 영구 삭제**입니다. 사용자가 직접 체크하고, 확인 창과 영구 삭제 확인 창에서 모두 [예]를 고른 경우에만 실행합니다
  ([모두 선택]·자체 검사는 고르지 않음). 다른 항목보다 먼저 비우고, 실패해도 나머지 정리는 계속합니다.

## 실제 확보 가능 용량

[시스템 정리]·[프로젝트 정리]의 실제 확보 용량(`reclaim`)은 정리 판정과 별개로, 표시만을 위해 셉니다. 무엇을 옮길지는 바꾸지 않습니다.

- 정리 항목 안의 파일마다 할당 크기·하드 링크 수·파일 ID를 조회합니다. Windows 11 24H2 이상은 `GetFileInformationByName`
  (`FileStatByNameInfo`)으로 파일을 열지 않고, 그 전에는 `FILE_READ_ATTRIBUTES`로만 열어(`FILE_FLAG_OPEN_NO_RECALL`, 공유 모두 허용) 조회합니다.
  파일 내용은 읽지 않으며 클라우드 파일을 내려받지 않습니다.
- 압축·스파스 파일은 `GetCompressedFileSizeW`의 실제 점유량, MFT에 상주하는 파일(할당 크기가 클러스터 배수가 아님)은 0입니다.
- 링크가 여러 개인 파일은 (항목, 파일 ID)로 모아, 항목 안에서 모든 링크를 봤을 때만 확보 가능으로 셉니다. 아니면 항목 밖에 링크가 남으므로
  공유(`shared_bytes`)로 셉니다. 재분석 지점(심볼릭 링크·정션)은 세지 않습니다.
- 조회하지 못한 파일은 열거로 얻은 할당 크기(없으면 논리 크기)로 추정합니다.
- 프로젝트 정리는 탐지와 같은 한 번의 열거에서 항목 안의 파일만 조회합니다. 시스템 정리는 정리 대상으로 남은 항목만 다시 훑어 조회합니다
  (최근 항목·보호 항목은 조회하지 않음).

## Booster

[부스터] 탭(`booster`)의 시작 프로그램·프로세스 관리는 파일을 지우지 않지만 시스템 동작을 바꾸므로 다음을 지킵니다.

- 시작 프로그램 끄기는 `...\Explorer\StartupApproved\(Run|Run32|StartupFolder)` 값만 바꿉니다(첫 바이트 홀수 = 끔, 끈 시각 기록).
  `Run` 값과 바로 가기는 그대로 두므로 [사용]으로 되돌리거나 작업 관리자에서 다시 켤 수 있습니다.
- 프로세스 끝내기 보호(하나라도 걸리면 끝내지 않음): PID 0·4와 세션 0, 다른 사용자 세션, Windows 필수 프로세스 이름, Windows 폴더 안의 실행 파일,
  ByteSieve 자신, 경로·시작 시각을 읽을 수 없는 프로세스.
- 끝내기 직전에 같은 PID를 다시 열어 시작 시각이 목록과 같은지(PID 재사용 방지), 아직 실행 중인지, 보호 판정을 다시 통과하는지 확인합니다.
