# 성능 측정

`bytesieve-bench`로 실행 시간·CPU 시간·최대 메모리와 스캐너 진단 값을 측정합니다.

```powershell
cmake --build build --config Release --target bytesieve-bench
build\Release\bytesieve-bench.exe --mode model --runs 3 C:\Windows     # --mode tree|model|cleanup, --threads N
```

최대 메모리는 프로세스 전체 기준이므로 모드마다 따로 실행하고, 첫 실행은 디스크 캐시가 차지 않았을 수 있어 두 번째 실행부터 봅니다.
실행마다 다음 줄로 스캐너 내부(결과 모델 제외)를 함께 보여 줍니다. 프로세스 메모리보다 흔들림이 적어 전후 비교에 씁니다.

```
       scanner: peak tasks 1043 (24.7 MiB) · prefetched 162311 · self 3 · waits 42083 · discarded 1394
```

| 값 | 뜻 |
|---|---|
| peak tasks (메모리) | 동시에 살아 있던 폴더 작업 수와 그 작업들(구조·경로·열거 결과·하위 폴더 칸)이 붙잡은 메모리의 최대 |
| prefetched / self | 작업 스레드가 미리 열거한 폴더 / 호출 스레드가 직접 열거한 폴더 |
| waits | 호출 스레드가 열거 중인 작업 스레드를 기다린 횟수 |
| discarded | 열거했지만 쓰지 않고 버린 폴더(제외·취소, 상한 때문에 내쫓은 것) |

최적화 전후를 비교할 때는 두 실행 파일을 같은 시간대에 번갈아(전 → 후 → 전 → 후) 돌려 디스크 캐시 상태 차이를 줄입니다.

## 측정 결과

Windows 11, 논리 프로세서 12개, `C:\Windows` 파일 21만·폴더 16만, 디스크 캐시가 찬 상태, Release:

| 모드 | 개선 전 | 개선 후(자동, 8 스레드) | 개선 후(`--threads 1`) |
|---|---|---|---|
| tree(집계만) | 16.4 s · 최대 12 MiB | **3.2 s** · 55 MiB | 12.6 s · 36 MiB |
| model(GUI 트리 구성) | 16.4 s · 64 MiB | **3.1 s** · 98 MiB | 12.6 s · 73 MiB |
| cleanup(정리 후보 탐지) | 16.6 s · 12 MiB | **3.3 s** · 57 MiB | 13.0 s · 36 MiB |

### 병렬 스캔 메모리 최적화

위 "개선 후"(병렬 미리 열거)에서 메모리를 줄인 결과입니다. 같은 조건에서 최적화 전후를 번갈아 3회씩 두 번 측정했습니다(8 스레드).

| 모드 | 동시 폴더 작업 수 | 스캐너 작업 메모리 | 프로세스 최대 메모리 | 시간 |
|---|---|---|---|---|
| tree | 52,000 → **1,040** | 34 → **24.7 MiB** | 58 → **39~41 MiB** | 3.1~3.4 s → 3.2~3.4 s |
| model | 51,000 → **1,030** | 34 → **24.7 MiB** | 106~110 → **87.5 MiB** | 3.2~3.4 s → 3.2~3.4 s |
| cleanup | 51,000 → **1,030** | 35 → **24.7 MiB** | 55.5 → **39~40 MiB** | 3.2~3.4 s → 3.4~3.5 s |

`--threads 1`: 동시 폴더 작업 33,045 → 14개, 스캐너 작업 메모리 22.0 → 21.6 MiB, 프로세스 36 → 33 MiB(시간 같음).
파일·폴더 수는 모든 실행에서 같았습니다.

- **원인**: 폴더를 열거하자마자 하위 폴더마다 작업(경로 사본·키, 약 670바이트)을 만들고, 작업 스레드가 있으면 모두 큐에 넣었습니다.
  큐에는 상한이 없어 5만 개가 넘게 쌓였고, 한 스레드에서도 `WinSxS`(하위 폴더 3만 2천 개)의 형제 폴더 작업이 22 MiB를 차지했습니다.
- **개선**: 하위 폴더는 32바이트 칸으로만 두고 작업은 열거하기 직전에 만들며, 큐 항목은 16바이트입니다. 미리 읽은 결과의 상한을
  65,536개·32 MiB에서 1,024개·2 MiB로 낮추고, 상한이 찼을 때는 가장 나중에 필요한 것을 내쫓아 급한 폴더가 막히지 않게 했습니다
  (내쫓아 버린 열거는 약 0.9%). 스택에 올리는 폴더는 남은 하위 폴더 기록만 남기고, 열거 버퍼의 늘림 여유는 줄입니다.
  작업 스레드는 넣은 항목 수만큼만 깨웁니다.
- **상한 정하기**: 상한을 바꿔 가며 측정했습니다. 1,024개·2 MiB 아래로는 메모리가 줄지 않았고(아래 바닥), 256개부터 호출 스레드가
  기다려 느려졌습니다(3.5~4.5 s).

  | 상한 | 시간 | 스캐너 작업 메모리 | 프로세스 최대 |
  |---|---|---|---|
  | 65,536개·32 MiB | 3.4~4.0 s | 33~40 MiB | 52~56 MiB |
  | 4,096개·8 MiB | 3.3~3.7 s | 27.5 MiB | 43~44 MiB |
  | **1,024개·2 MiB** | **3.3~3.8 s** | **24.7 MiB** | **38 MiB** |
  | 256개·512 KiB | 3.5~4.5 s | 24.7 MiB | 38 MiB |

- **남은 바닥**: 폴더 하나는 처리할 때까지 목록 전체를 들고 있어야 합니다. `C:\Windows`에서는 `WinSxS`(하위 폴더 3만 2천 개, 약 8 MB)와
  `WinSxS\Manifests`(파일 4만 4천 개, 약 11 MB)가 동시에 열려 있는 순간이 스캐너 메모리의 대부분입니다.
- **CPU 시간**: 8 스레드의 CPU 시간(약 25초)은 1 스레드(약 12초)의 두 배이며 최적화 전후가 같습니다. 스레드 수를 바꿔 보면
  (2개 16~18 s, 4개 19~20 s, 8개 25 s) 폴더 하나를 읽는 커널 비용이 스레드가 늘수록 커지는 것이라 작업 분배 쪽 낭비는 아닙니다.
  경과 시간은 스레드가 많을수록 줄어(2개 8.3 s, 4개 4.8 s, 8개 3.3 s) 기본값(최대 8개)을 그대로 둡니다.

### GUI 스캔 완료 처리 점검(2026-11-14)

GUI에서 스캔이 끝난 뒤 UI 스레드가 하는 일을 단계별로 쟀습니다(측정용 타이머는 측정 후 제거). `C:\Windows`(폴더 17만 개), Release,
디스크 캐시가 찬 상태에서 `bytesieve-gui --self-test`로 4~6회 돌렸습니다(`BYTESIEVE_HISTORY_DIR`로 임시 기록 폴더, 직전 기록이 있는 상태).

| 단계 | 시간 | 판단 |
|---|---|---|
| 스캔(작업 스레드) | 3.4~3.7 s | `bytesieve-bench --mode model`(3.7~3.8 s)과 같음. 진행 중 화면 갱신 비용은 측정 편차 안 |
| 모델 넘겨받기·상태 줄 | 1 ms 안팎 | — |
| 트리맵·트리·순위 목록 표시 | 약 38 ms(트리맵 12, 트리 2, 순위 23) | 충분히 짧음, 그대로 둠 |
| **직전 기록과 비교·저장(`history_track`)** | **220~340 ms**(첫 기록만 저장하면 57 ms) | UI 스레드에서 창이 멈춤 → 개선 |

`history_track` 안을 다시 나누면 스냅숏 만들기 15~25 ms, 직전 기록 읽기 33~48 ms(가끔 디스크 때문에 100~400 ms), 비교(`history_diff`)
**150~195 ms**, 저장 30~40 ms였고, 비교 안에서는 키·해시표 만들기 70~99 ms, 조회 48~55 ms, 정렬 0 ms였습니다.

- **원인**: 비교가 항목(양쪽 17만 개씩)마다 대문자 키를 두 번 만들었습니다(해시표를 만들 때 한 번, 상대 쪽 표에서 찾을 때 또 한 번).
  키마다 `malloc` + `CharUpperBuffW`가 약 68만 번, 해시 계산도 같은 문자열에 두 번씩이었습니다.
- **개선**(`scan_history.c`): 항목마다 키와 해시를 한 번만 만들어 해시표와 조회가 함께 씁니다. 키는 한 버퍼에 이어 두고
  `CharUpperBuffW`를 한 번만 부르며(글자마다 따로 바꾸므로 키마다 부른 것과 같음), 해시표 칸에는 항목 번호만 두고 해시가 같을 때만
  문자열을 비교합니다. 비교 규칙(대소문자 무시, 깊이 맞추기, 같은 경로는 처음 것)은 그대로입니다.

| | 비교(`history_diff`) | 비교·저장 전체(`history_track`, 보통) |
|---|---|---|
| 개선 전 | 150~195 ms | 220~340 ms |
| 키 한 번 만들기(중간 단계) | 120~150 ms | 220~265 ms |
| **개선 후** | **50~56 ms** | **137~171 ms** |

- **정합성**: 개선 전·후 `disk-scanner --track`을 같은 기준 스냅숏 사본으로 같은 폴더(폴더 2,400개 + 한글·`ß`·`ı`·`Ǆ`·이모지(서로게이트 쌍)
  이름, 늘어남·줄어듦·새 폴더·삭제·대소문자만 바꾼 이름)에 돌려 출력이 바이트 단위로 같음을 확인했습니다(기록 폴더 경로 줄 제외).
  `scan_history` 단위 테스트에 대소문자만 다른 키(라틴 확장·한글·서로게이트 쌍) 검사를 더했고, 개선 전 코드에서도 같은 결과로 통과합니다.
- **그대로 둔 것**: 직전 기록 읽기가 가끔 튀는 것은 아래 "직전 기록 읽기 지연 분석"에서 원인을 좁혔고 코드는 바꾸지 않았습니다.
- **자원**: 언어 4개 전환 + DPI 144 → 192 → 96 전환을 5번 반복해도 GDI 개체 95 → 97(첫 회만), USER 개체 151 → 151로 늘지 않았습니다(누수 없음).
- 스캐너·정리 동작은 바꾸지 않았습니다.

### 비교·저장을 UI 스레드 밖으로(2026-11-14)

위 개선 뒤에도 남은 비교·저장(140~170 ms, 직전 기록 읽기가 느리면 수백 ms)을 작업 스레드로 옮겼습니다(`gui_scan.c`).

- **흐름**: 스캔이 끝나면(`WM_APP_SCAN_DONE`) UI 스레드는 모델을 받아 두고 비교·저장 작업 스레드만 시작합니다. 작업 스레드는 모델을
  읽기만 하고 직전 기록과 비교·저장한 뒤 `WM_APP_HISTORY_DONE`을 보냅니다. UI 스레드가 결과를 가져와 예전과 같은 순서로 반영합니다
  (진행 막대·상태 줄 → 단추 → 비교 결과 → 기록 삭제 단추 → 분석 줄 → 트리맵·트리·순위 목록 → 완료 알림). UI 갱신은 모두 UI 스레드에서 합니다.
- **작업 중 상태**: 끝날 때까지 바쁜 상태입니다(움직이는 막대, 다시 스캔·경로 바꾸기·취소·기록 삭제·내보내기 막음, 완료 문구·결과 없음).
  그래서 중복 실행이 없고, 작업 스레드가 읽는 모델을 UI가 바꾸지 않으며, 끝나지 않은 결과를 완료로 보이지 않습니다. 저장 여부는 시작할 때 값으로 정합니다.
- **취소·창 닫기·예외**: 스캔이 끝난 뒤라 취소 단추는 꺼 두고 저장은 끝까지 합니다(파일을 반쯤 쓰지 않음). 창을 닫으면 작업이 끝나기를
  기다린 뒤 모델을 해제합니다. 작업 스레드를 만들지 못하면 예전처럼 UI 스레드에서 합니다. 비교·저장 실패는 예전과 같이 분석 줄에 알립니다.

UI 스레드를 한 번에 붙잡는 시간(`C:\Windows`, Release, 직전 기록이 있는 상태, 10회, 측정용 타이머는 측정 후 제거):

| | 평균 | p95 | 최댓값 |
|---|---|---|---|
| 개선 전: 스캔 완료 처리(비교·저장 + 결과 표시) | 313 ms | 671 ms | 671 ms |
| 개선 후: 스캔 완료 처리 | 0.5 ms | 0.6 ms | 0.6 ms |
| 개선 후: 비교 완료 처리(결과 표시) | 40.2 ms | 43.5 ms | 43.5 ms |

개선 후 가장 긴 멈춤은 결과 표시(트리맵·트리·순위 목록, 약 38 ms)입니다. 회귀 테스트 `gui_history_async`·`gui_history_close`는 비교·저장을
UI 스레드에서 하던 예전 동작에서는 실패하는 것을 확인했습니다.

| **새로 쓴 파일, 같은 프로세스가 앱 스캐너로 스캔 후 열기** | **55.4 ms** | **517.7 ms** | **517.7 ms** |
| 위와 같되 모델을 해제하고 열기 | 60.7 ms | 274.9 ms | 274.9 ms |
| 위와 같되 스캔 뒤 3초 기다렸다 열기 | 10.0 ms | 12.5 ms | 12.5 ms |

- **원인 좁히기**: 지연은 모두 **열기**에서 생기고, 읽기(캐시 우회해도 2.2 ms)·파싱(약 20 ms)·메모리(페이지 폴트 일정)는 흔들리지 않습니다.
  디스크 I/O나 파싱 비용 문제가 아닙니다. 지연은 "새로 쓴 파일"을 "앱 스캐너(폴더마다 핸들을 여는 병렬 스캔, 약 17만 번)가 끝난 직후 같은
  프로세스에서" 처음 열 때만 재현되고, 오래된 파일이거나 다른 프로세스·다른 열거 방식이거나 3초 기다리면 사라집니다. 모델 크기와는 관계없습니다.
- **외부 요인**: 이 PC는 Windows Defender 실시간 보호(액세스 시 검사·동작 모니터링)가 켜져 있습니다. 새 파일을 처음 열 때의 실시간 검사가
  직전의 대량 열기로 밀린 처리 때문에 늦어지는 것으로 보는 것이 측정과 가장 잘 맞습니다(보안 설정은 바꿀 수 없어 끄고 비교하지는 않았습니다).
- **영향**: 비교·저장을 작업 스레드로 옮겨 이 지연은 UI를 멈추지 않습니다(작업 중 상태가 그만큼 길어질 뿐). 코드는 바꾸지 않았습니다.

## 병목 분석과 개선

- 개선 전 CPU 시간의 97%가 커널의 폴더 열기·열거였습니다. 열거 API를 `FindFirstFileW`에서 폴더 핸들 + `GetFileInformationByHandleEx`로
  바꿔 한 스레드 기준 16.3초 → 12.4초로 줄였고(할당 크기도 함께 얻음), 병렬 미리 열거로 3초대가 되었습니다.
- 병렬 미리 열거로 늘었던 메모리는 위 최적화로 줄였습니다. 메모리가 더 중요하면 `--threads 1`을 쓰세요.
- 모델은 폴더 이름을 하나의 문자열 저장소에 담아 해제 시간이 10ms → 3ms로 줄었습니다.

병렬 미리 열거의 동작 방식은 [architecture.md](architecture.md#병렬-미리-열거)를 참고하세요.
